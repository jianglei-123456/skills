# DBX — output shapes

Read this when you need to parse dbx output, not just read it: which JSON fields exist, which field tells you a result was cut short, and how failures arrive. Collected from a live CLI; field sets are what a current build emits and may gain fields over time.

## doctor

```json
{
  "appDataDir": "…\\com.dbx.app",
  "dbPath": "…\\com.dbx.app\\dbx.db",
  "dbPathExists": true,
  "connectionsTableExists": true,
  "connectionRowCount": 27,
  "loadConnectionsOk": true,
  "loadedConnectionCount": 27,
  "bridgePortFile": "…\\mcp-bridge-port",
  "bridgePortFileExists": true,
  "bridgeUrl": "http://127.0.0.1:10332",
  "directQueryTypes": ["postgres", "redshift", "mysql", "sqlite", "…"],
  "bridgeRequiredTypes": ["clickhouse", "oracle", "mongodb", "…"]
}
```

Read `loadConnectionsOk` and `loadedConnectionCount` to know whether the connection store is usable; `bridgePortFileExists` plus `bridgeUrl` tell you whether the Desktop bridge is up.

## capabilities

```json
{ "directQueryTypes": ["…"], "bridgeRequiredTypes": ["…"] }
```

## connections list

```json
{
  "connections": [
    { "name": "prod_192.168.5.17_machine", "type": "postgres",
      "host": "192.168.5.17", "port": 19990, "database": "machine" }
  ]
}
```

`database` is omitted when the connection does not set one. CSV form: `name,type,host,port,database`.

## schema list

```json
{
  "connection": "prod_192.168.5.17_machine",
  "schema": "public",
  "tables": [ { "name": "c_machine", "type": "BASE TABLE" } ]
}
```

`schema` appears only when `--schema` was passed. `type` distinguishes `BASE TABLE` from views.

## schema describe

```json
{
  "connection": "prod_192.168.5.17_machine",
  "table": "c_machine",
  "columns": [
    {
      "name": "id",
      "data_type": "bigint",
      "is_nullable": false,
      "column_default": null,
      "is_primary_key": true,
      "is_unique": false,
      "extra": "generated by default as identity (start with 1 increment by 1)",
      "comment": null,
      "numeric_precision": null,
      "numeric_scale": null,
      "character_maximum_length": null
    }
  ]
}
```

`data_type` is the database's own spelling, often already carrying a width — `character varying(40)`, `timestamp without time zone`. `extra` holds identity/generated clauses. `comment` is the database comment, independent of notes files.

## context

```json
{
  "connection": "prod_192.168.5.17_machine",
  "database": "machine",
  "schema": "",
  "truncated": true,
  "tables": [
    { "name": "_area_updated_day", "type": "BASE TABLE", "columns": [ /* schema describe column objects */ ] }
  ]
}
```

**`truncated` is the field that matters.** `true` means `--max-tables` (or a build-internal cap) dropped tables from the response. The plain-text form of this command omits the flag entirely: a text schema dump that looks complete may not be. Check `truncated` in JSON, or re-run with a larger `--max-tables`, before treating the schema as the whole database.

Plain text shape, for cost-sensitive prompting:

```
Connection: prod_192.168.5.17_machine
Database: machine

## c_machine
Type: BASE TABLE
- id bigint NOT NULL PK
- machinery_code character varying(100) NULL
```

## query

```json
{
  "connection": "prod_192.168.5.17_machine",
  "columns": ["a", "b"],
  "rows": [ { "a": 1, "b": "x" } ],
  "row_count": 1
}
```

- `columns` is the authoritative column order; row objects are keyed by column name.
- `row_count` is the number of rows **returned**, not matched. `row_count` equal to your `--limit` means the result was probably cut short — re-query with `ORDER BY` and a `WHERE` bound rather than paging on hope.
- Values keep their JSON types (`1`, `"x"`, `null`), so timestamps and numerics arrive as strings or numbers per driver, untyped by the CLI.
- CSV form: header line of `columns`, then values; suitable for `--format csv` piping.

Queries that fail at the database level still return `{ "error": … }` with `"code": "ERROR"` — see [Errors](#errors).

## dbml

No JSON mode. Success is the line `Wrote <n> bytes to <path>`; without `--out` the DBML text is the output. Emitted blocks: `Project`, `TableGroup`, `Table` (columns with `[pk]`, `[not null]`, `[unique]`, `Note:` lines, `Indexes { … }`), and `Ref` for derived relationships. `warning:` lines on stderr say which metadata the database could not supply.

## docs

No JSON mode (`--json` is ignored). With `--out`: `Wrote <n> bytes to <path>`. Without `--out`: an entire `<!doctype html>` document on stdout — never let that reach an agent's context.

## open

```json
{ "opened": true, "connection": "prod_192.168.5.17_machine", "table": "c_machine" }
```

## Errors

Two envelopes, and which one you get depends on whether the failure reached the command runtime or the option parser.

**JSON envelope** — printed on stdout under `--json`, exit code non-zero:

```json
{ "error": { "code": "CONNECTION_NOT_FOUND", "message": "Connection \"nope_conn\" not found." } }
```

Database-level failures use `"code": "ERROR"` with the driver message in `message`. Parse `error.code` first; `message` is for the human. Full code table in [troubleshooting.md](troubleshooting.md).

**Plain envelope** — printed on stderr, whatever the output format, exit code non-zero:

```
Error [UNKNOWN_OPTION]: Unknown option: --nope
Error [INVALID_ARGUMENT]: dbx schema describe expects 3 argument(s); received 2.
Error [NOTES_INVALID]: Notes file … has formatVersion 99, but this build understands 1.
```

So an agent should treat a non-zero exit as failure regardless of stdout, and check both patterns: `Error [CODE]: message` on stderr, or `error.code` in JSON on stdout.
